## 1. Context & Architectural Overview
ASTCV (Adaptive Screen-Timestamped Computer Vision) operates as an **active closed-loop verification engine**.
Rather than passively analyzing a facial stream (which is susceptible to virtual camera injection and static deepfakes), ASTCV introduces an active physical feedback loop:
1. **Screen Emitter (M1 / M2):** Displays a randomized, high-frequency challenge pattern on screen.
2. **Camera Sensor (M2):** Captures the subject's face reacting and reflecting the emitted pattern.
3. **Synchronization Engine (M2):** Matches emitted patterns to captured frames using monotonic hardware clocks (`performance.now()`).
4. **Data Engine (M3):** Validates the data contract, ingests session video, logs jitter metrics, and feeds aligned face regions into M1's reflectance physics model.

```
       [M1: Challenge Engine]
                 │ (Randomized pattern, nonce, frequency)
                 ▼
       [M2: Screen Emitter UI]
                 │ (Photonic emission onto subject's skin)
                 ▼
       [Physical Face & Eyes]
                 │ (Diffuse Lambertian & Specular Phong reflection)
                 ▼
       [M2: WebRTC Capture Pipeline]
                 │ (Frame telemetry + Hardware timestamps)
                 ▼
       [M2: Timestamp Sync Matching]
                 │ (MatchedSyncPair list + SessionManifest)
                 ▼
       [M3: Data Engine & Session Storage] ──► [MLflow Experiment Tracker]
                 │ (Validated & aligned 256x256 crops)
                 ▼
       [M1: Physicality Scoring Model]
```

## 2. Telemetry Schema & Payload Specifications

### 2.1 Screen Challenge Pattern (`ScreenChallengePattern`)
Generated by M1's algorithm and rendered by M2's browser/native UI:
```json
{
  "pattern_id": "c9a18f2b",
  "sequence_index": 42,
  "timestamp_emitted_ms": 14205.82,
  "color_rgb": [255, 120, 60],
  "frequency_hz": 8.5,
  "spatial_zone": "FOREHEAD",
  "nonce_token": "a8f3b29c1e4d"
}
```

* **Constraints:**
  - `frequency_hz`: Bounded between 0.5 Hz and 15.0 Hz for photosafety compliance.
  - `nonce_token`: Cryptographically secure random token preventing pattern guessing by adversarial neural networks.

### 2.2 Camera Frame Telemetry (`FrameCaptureTelemetry`)
Recorded by M2's WebRTC capture receiver:
```json
{
  "frame_index": 42,
  "timestamp_captured_ms": 14232.14,
  "exposure_time_ms": 16.6,
  "reported_fps": 30.0,
  "frame_width": 1280,
  "frame_height": 720,
  "frame_checksum_sha256": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
}
```

### 2.3 Matched Synchronization Pair (`MatchedSyncPair`)
Constructed by M2's sync engine linking emitted pattern to camera response:
```json
{
  "pair_id": "pair_0042",
  "pattern": { ... },
  "frame": { ... },
  "display_to_capture_delta_ms": 26.32,
  "sync_status": "SYNCHRONIZED",
  "estimated_ambient_lux": 180.0
}
```

$$\Delta_i = t_{\text{captured}, i} - t_{\text{emitted}, i}$$

## 3. Cross-Device Jitter & Network Tolerance Metrics
For Phase 1 deliverables, cross-device jitter testing must satisfy:
1. **P95 Latency Delta:** $\le 50.0 \text{ ms}$.
2. **Frame Drop Rate:** $< 5.0\%$.
3. **Clock Monotonicity:** Both emitter and capture timestamps must use monotonic browser high-res clocks (`performance.now()`) with no backwards drift.

## 4. Master Session Storage Hierarchy
Every live capture session ingested by M3 is organized as:
```
data/sessions/
└── {session_id}/
    ├── manifest.json                  # Pydantic SessionManifest
    ├── session_video.mp4              # Full recorded session video
    ├── calibration_matrix.json        # M2 display-camera color chart calibration (Phase 2)
    └── crops/                         # Aligned 256x256 face crops with spatial annotations
```
